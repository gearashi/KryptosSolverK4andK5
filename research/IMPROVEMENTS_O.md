# Phase O: search work, validation and durable research

Version 0.4.0 implements the fourteen bounded changes in
[the pre-experiment plan](phase_O_plan.json). The primary efficiency criterion
is fewer search decisions or complete candidate evaluations for the same
correct result. Factor operations, checkpoint verification, calibration and
elapsed time are recorded separately. Supporting workflow features are not
described as cipher-solving shortcuts.

| # | Improvement | Meaning and acceptance evidence |
| --- | --- | --- |
| 1 | Competing-family benchmark | Four authored 97-letter controls retain three distinct feasible plaintext families before scoring. Generating-text ranks are observations, not a required success outcome. |
| 2 | Repeated whole-bank null controls | Every shuffled input reruns all methods and language models. Censoring suppresses the empirical rate. This is not an authenticity probability. |
| 3 | Incremental exact CPU scoring | Only affected ngram factors are recomputed; dense changes use a full score. Candidate coverage and exact ranking are unchanged. |
| 4 | Coordinated key moves | Connected pairs can cross interaction barriers. Trials and factor work are counted; unfavorable small controls remain in the report. Default off. |
| 5 | Joint route/key pruning | Admissible window bounds eliminate unfinished branches strictly below the top-k cutoff. Ties and exact recipes survive. Default off. |
| 6 | Capped mini-bucket bounds | Separate factor-group maxima provide an upper bound when exact combined elimination is too large. Resource caps fall back safely. Default off. |
| 7 | GPU survivor filtering | Certified interval survivors are selected on the GPU, followed by exact CPU comparison. This reduces explicit transfer on the recorded pages, not candidate coverage. |
| 8 | Measured backend choice | Optional bounded CPU/CUDA calibration requires agreement and caches the selected device. Calibration adds work; default policy is unchanged. |
| 9 | Parameterized sculpture paths | Bounded ordinal-grid walks retain every alias but fit each distinct valid permutation once. Trapped paths are explicit. |
| 10 | Joint search continuation | Durable pure-JSON frontiers preserve cumulative search coverage. Saved-candidate rechecking and repeated preparation remain separately visible. |
| 11 | Drafts and personal presets | Incomplete editing state survives refresh without starting computation; stale-tab writes are rejected. |
| 12 | Searchable, tagged, archived history | Lightweight summaries paginate without copying large result objects. Archiving changes visibility and is reversible. |
| 13 | Diagnostics and recovery | Damaged records remain on disk. Bounded hashed backups restore separate read-only evidence; imported checkpoints never execute. |
| 14 | Clean-package release gate | Windows/Linux Python 3.10/3.12 CI checks a Git archive and browser workflows. Actual local CUDA evidence is separate; publication verifies gearashi, tag and asset hashes. |

## Evidence and interpretation

Canonical records use the installed computation-audit v2 runner and immutable
source snapshots. Commands and contracts are generated by `run_O_audit.py`.
Each kind requires a fresh label; preparation refuses changed source bytes.

```text
python research/run_O_audit.py --audit-skill PATH --label release-O-001 --kind search
python research/run_O_audit.py --audit-skill PATH --label release-O-001 --kind validation
python research/run_O_audit.py --audit-skill PATH --label release-O-001 --kind scan
```

The scan audit requires actual CUDA hardware. Source-specific protocols and
limitations are in [search notes](search_O_notes.md),
[validation notes](validation_O_notes.md), and the
[independent integration review](O-engine-independent-review.md) and
[bound proof review](O-bound-proof-review.md).
Current package and browser results are indexed in
[release-validation.json](release-validation.json).

These controls do not establish Kryptos's actual cipher, an authenticated K4/K5
solution, a universal search improvement, or a meaningful probability that a
high-scoring candidate is correct. New heuristic and stronger-bound options
remain explicit choices because they can add work on unfavorable problems.

See [search controls](../docs/SEARCH_STRATEGIES.md) and
[workspace/release operations](../docs/WORKSPACE_AND_RELEASE.md) for use and limits.

not general reductions in total work. Persistence and release features address
repeated manual work and reliability; their presence alone proves nothing about
cryptanalytic efficiency.
